## 0. Architecture invariants (do not break)

From `README.md:7`, `docs/ARCHITECTURE.md:7-10`, `todo.md:29-37`, `PHASE_4_REPORT.md:95`: **one computer, one underlying environment, multiple historical presentations**. One real host filesystem, one set of user data, one shared capability layer. Explicitly out of scope: virtual disks, per-skin filesystems, duplicated homes/accounts, a host/virtual storage selector, or artificial separation of desktop content. Per-skin *visual* state (icon positions, wallpaper) is fine.

---

## 1. Executive summary

The platform genuinely delivers the "one computer, many skins" model. All eight registered skins read the same real desktop/filesystem through a single preload bridge; filesystem, permission, and IPC hardening are real and tested; skin switch lifecycle now cleans up watchers and recovers from failed mounts; the shared application framework (`DTMApps`) is loaded by every skin. The latest working tree also contains substantial in-flight UX work (Aqua shell chrome for Mac skins, shell-window parking, real Trash drag/drop, notepad/calc/paint taskbar routing) and the test suites pass on it.

The most important remaining gaps are not in the core filesystem abstraction; they are at the edges:

1. **Unverified automatic download and silent install of a third-party browser at startup** (supply-chain risk).
2. **Skins are not isolated despite documentation calling them sandboxed** — same-origin `file://` iframes with the full host-wide `DTM.fs` bridge; generated skins are a real trust problem.
3. **The shell control channel (`postMessage`) has no source/origin validation**, and renderer-side URL normalization allows arbitrary schemes, relying on a single downstream guard.
4. **Shell-window chrome is chosen at window creation**, so open Discord/browser windows keep the previous OS's decorations after an era switch; the cold-start `dtm:skin-changed` event is also never emitted, requiring a consumer workaround.
5. **Seven of eight skins are monolithic, duplicated single-file documents**; the documented SDK/template is not how shipped skins are built.
6. **Permission policy blocks media requests outright**, while the README implies a user-consent prompt can grant them — functional and documentation gap.
7. **No CI, lint, packaging, code-signing, or fast unit-test tier**; all verification is Electron GUI-driven with fixed sleeps.

Recommended order of work is in §5. Nothing in this audit requires changing the product's one-computer model.

### 2.2 What is actually shared versus per-skin

| Shared (engine / main process) | Per skin (presentation) |
|---|---|
| Real filesystem API (`DTM.fs`) and path policy | Wallpaper, colours, cursors, fonts |
| Desktop items, icon positions, live FS events | Desktop layout widgets, icon artwork |
| Host drives, shortcuts, Recycle Bin, network, tray, volume | Menu bars, Start menus, Docks, Deskbar |
| Window registry, shared apps (Notepad/Calc/Paint/etc.), dialogs | Window chrome, animations, sounds |
| Shell-hosted web apps (Discord, IE, Safari, WMP) | Language ("Netscape" vs "IE", Trash vs Recycle Bin) |
| Skin registry, switching, persistence of active skin | Visual preferences stored per skin id |

The shared model is enforced by tests (`test/shared-computer.js`: 5/5 pass, including "no per-skin private file store is created"). Per-skin icon positions are the only documented per-skin persistence (`desktop-mirror.js:285-295`, key `dtm:icon-positions:<skinId>`).

### 2.3 Main runtime flows

- **Filesystem:** skin → `DTM.fs.*` → `dtmPreload` IPC → sender check → `filesystem-service.js` → `isSafePath`/`isProtectedPath` → Node `fs`. Text/binary capped at 8/64 MB, listings at 20,000 entries.
- **Desktop mirror:** `DTM.desktop.getItems` (1.5 s cache, 10 s timeout) → `dtm:fs-desktop` → real desktop paths + `fs.watch` subscriptions → `dtm:fs-changed` / `dtm:fs-icons-changed` → debounced re-render of each live skin mirror. `unmountDesktop()` disposes listeners/watchers (`desktop-mirror.js:297-362`).
- **Shell apps:** skins call `window.parent.postMessage({type:'dtm:launch-webapp', ...}, '*')` or the Mac Dock posts `dtm:webapp-park`; `shell-apps.js` creates `<webview>` windows in the top document because webviews cannot live in the skin iframe.
- **Skin switching:** `skin-manager.js:282-367` unmounts the old desktop, loads a new iframe, waits for `#desktop`, restores the previous or recovery skin on failure, persists `dtm_active_skin` in `localStorage`. Startup mount (`mountActiveSkin`) does **not** emit `dtm:skin-changed`.
- **External browser:** `browser.js` prefers Ungoogled Chromium (`chromium.js`, BiDi over DevTools) and falls back to Waterfox (`waterfox.js`); URLs are validated via `isSafeExternalUrl` (http(s) + hostname). On first launch `main.js:86-99` calls `browser.ensure()`, which may download and silently install Chromium.

## 4. Findings (prioritised)

### F1 — High: automatic, unverified third-party browser install at startup
**Evidence:** `electron/main/browser-setup.js:22` queries the GitHub "latest release" API; `:100-167` follows redirects and downloads the asset to a temp path (only length/redirect checks); `:174-183` runs the installer with `/silent /install`; `:217` runs PowerShell to create a shortcut. `electron/main/main.js:86-99` triggers this on every first load. `README.md:79-91` documents the behaviour; `PHASE_4_REPORT.md:85` defers verification.
**Impact:** arbitrary code executes as the current user if the release asset, transport, or GitHub response is compromised; no pinned version, hash, Authenticode verification, offline-default, or user confirmation. This is the largest remaining host-level attack surface.
**Next action:** pin an exact browser version + SHA-256 (and ideally signature) in a checked-in manifest, verify before execution, fail closed with a visible message, and prefer a bundled installer / opt-in provisioning. Add a test that a hash mismatch prevents execution.

### F2 — High: skin "sandbox" is documentation, not an isolation boundary
**Evidence:** `src/index.html:33` creates `#skin-viewport` with no `sandbox` attribute; `skin-manager.js:241` assigns `iframe.src` directly. Same-origin `file://` skins can reach `window.parent.DTM` (`engine.js:59-117`: read/write/remove/move/recycle over the real host filesystem) and the parent DOM. `README.md:119` correctly says "treat skins as trusted application code"; but `docs/LLM_SKIN_GENERATION.md:68`, `:219-226`, `:328` say skins run in "sandboxed iframes", that generated skins are untrusted until reviewed, and that the bridge protects the host — which this code does not provide. `PHASE_2_REPORT.md:62` claims "NONE IDENTIFIED" coupling and full isolation; also stale.
**Impact:** a generated or modified skin can read/alter/delete most user files, intercept shell control messages, and manipulate the host shell UI. The permission policy is host-wide by design (`PHASE_4_REPORT.md:86`), so a process boundary would be needed for real containment.
**Next action:** decide and document one policy: (a) short term — shipped/generated skins are trusted code, remove the sandbox claims, add a mandatory human review gate for LLM output, and keep the existing host-wide policy honest; or (b) long term — `sandbox="allow-scripts"` + structured postMessage RPC + per-capability tokens, migrating skins off direct parent access. Do not imply (b) exists today.

### F3 — Medium: unvalidated shell control channel and scheme passthrough
**Evidence:** `src/components/ShellApps/shell-apps.js:1629-1649` handles `dtm:launch-webapp`, `dtm:safari-navigate`, `dtm:safari-action`, etc. from any `message` event with no `event.source`/`event.origin` check; `src/index.html:90-94` opens the era switcher on any matching string message. By contrast `window-registry.js:156-162` does validate `event.source`. `shell-apps.js:349-354` `normalizeUrl()` only prepends `https://` when no scheme is present; arbitrary `file:`/`data:`/`javascript:` inputs survive renderer-side validation. `webview-security.js:18-44` currently blocks non-http(s) navigation, so this is defence-in-depth, not a proven remote exploit (guests are separate WebContents and cannot postMessage to the top frame).
**Impact:** any script with a reference to the top window can open/park/navigate shell windows; a future change to webview hardening would turn URL passthrough into a host-file exposure. Inconsistent trust checks make the boundary hard to reason about.
**Next action:** validate `event.source === skinFrame.contentWindow || event.source === window` in every shell message listener, define a small typed message schema, and enforce `http(s)` in `normalizeUrl` (mirroring `isSafeExternalUrl`).

### F4 — Medium: shell chrome does not follow the active skin on live switches; cold-start event missing
**Evidence:** `shell-apps.js:29-33` reacts to `dtm:skin-changed` only by closing Safari windows; normal shell windows are left open. Mac-ness is computed when a window is created (`:371`, `:527`) and cached in `entry.isMac` (`:573`, used for toolbars/titles at `:655`, `:928`, `:1016`, `:1081`, `:1212`). The uncommitted work adds `currentSkinId()` (`:35-49`) to fix *cold starts*, but not live switches. `skin-manager.js:249-280` never emits `dtm:skin-changed` after the initial mount, so consumers must poll current state (exactly what the workaround does).
**Impact:** open Discord/browser windows keep Windows chrome after switching to Mac OS X (and vice versa), contradicting the product's core presentation promise; the todo item "Discord opens in a Microsoft Windows window" is only partly resolved in the working tree.
**Next action:** on `dtm:skin-changed`, close or rebuild open shell windows (or repaint them by re-applying `mac` classes and rebuilding controls), and emit the event after a successful initial mount. Add a regression test: open Discord on Mac OS X, cycle all eight skins, assert chrome/title matches the active skin.

### F5 — Medium: seven monolithic skins, duplicated implementations, SDK/template not used by shipped skins
**Evidence:** `windows98/desktop.html` is ~139 KB (one physical line before the current uncommitted edit), `windows95/desktop.html` ~96 KB; the other six single-file skins are 17–49 KB each; `macosx/` is the only modular skin (`desktop.js` 742 lines, `apps.js` 534, `finder.js` 207, `desktop.css`). Total skin assets ≈482 KB. `setupExplorer` is duplicated in Win95/Win98, `openApp` in four skins, window chrome in all eight. `templates/skin-template/` (8 files) and `docs/SKIN_SDK.md`/`LLM_SKIN_GENERATION.md` describe a modular SDK pattern the shipped skins do not follow. The working-tree Win98 diff alone is >200 KB, illustrating review cost.
**Impact:** fixes are multiplied by eight, regressions are hard to spot, and LLM-generated skins drift from the real codebase. This is the main long-term maintainability risk.
**Next action:** keep `DTMApps` as the shared-app layer, then incrementally extract shared UI primitives (window chrome, menus, dialogs, taskbar/dock adapters) into `src/components/`; convert one skin per release (Win95 → Win98 first), make the template canonical, and add a conformance test (manifest + `#desktop` + `DTMApps` registration + no direct IPC calls).

### F6 — Medium: verification is broad but shallow; no CI, lint, or release packaging
**Evidence:** all suites pass (§3), but `test/verify-all.js:60-81` relies on fixed 1.5–1.8 s sleeps and mostly asserts DOM presence; no automated coverage for the new Trash drag/drop, shell parking, or shared-app taskbar routing; `PHASE_4_REPORT.md:81,88` notes no lint config and untestable OS dialogs. No `.github/` workflow, no `electron-builder` config, no code-signing setup; `package.json` only has `start`/`test` scripts and `electron` devDependency.
**Impact:** regressions in timing-sensitive UI and uncommitted work can pass CI-by-hand; there is no reproducible signed installer for distribution.
**Next action:** add a fast Node-only unit tier for `permissions.js`, `permission-policy.js`, and manifest validation; a lint config; PR CI running `npm run verify`; focused regression tests for recycle/park/theme-switch; and packaging + signing configuration with an explicit release checklist.

### F7 — Medium: media permissions are denied outright but documented as prompt-based
**Evidence:** `permission-policy.js:19-33` has an empty request allowlist, so `main.js:43-57` calls back `false` for camera/mic/geolocation/notification/clipboard/display-capture; `README.md:117` says these are "denied unless a user grants them through a system prompt"; `PHASE_4_REPORT.md:87` says an explicit consent flow is future work.
**Impact:** Discord voice/video and screen share cannot work, and users get a silent failure rather than an explanation; documentation overstates behaviour.
**Next action:** either implement an in-app consent UI that grants only the specific permission for the specific origin after explicit user action (with OS picker retained for display capture), or change the documentation and show a friendly "blocked by Desktop Time Machine" message when a guest requests media.

### F8 — Low: stale architecture/report docs and small metadata drift
**Evidence:** `docs/ARCHITECTURE.md:92` lines describe the 2025-era four-component picture and omit the desktop mirror, `DTMApps`, shell web apps, permission policy, and external browser details; `PHASE_2_REPORT.md:52-62` claims non-existent APIs and full isolation; `README.md:32` says TempleOS 2013 while `src/skins/templeos/manifest.json` says `era: 2017`, `period: 2013–2017`; `README.md:130` links only Phase 2/3 reports. `docs/SKIN_API_REFERENCE.md:6-12` is the exception: it clearly marks planned APIs as not implemented.
**Impact:** contributors and reviewers get contradictory guidance; the phase reports are useful history but must not be read as current architecture.
**Next action:** rewrite `ARCHITECTURE.md` to match §2 of this audit, add a banner to phase reports marking them historical, reconcile TempleOS metadata, and link this audit from the README.

### F9 — Low: main window preload runs unsandboxed
**Evidence:** `electron/main/window-manager.js:38` sets `sandbox: false` "Allows preload to bridge Node APIs securely"; mitigations are `contextIsolation: true`, `nodeIntegration: false`, and a controlled bridge.
**Impact:** larger blast radius if renderer code ever escapes isolation than a fully sandboxed preload would allow. Current tests confirm the bridge is restricted, so this is hardening, not an active bug.
**Next action:** evaluate `sandbox: true` in a branch; the preload only needs `contextBridge`/`ipcRenderer`, so it may migrate cleanly. Keep the change gated on the full verify suite.

### F10 — Low: some PowerShell invocations resolve from PATH instead of System32
**Evidence:** `desktop-integration.js:53` and `:1113`, `window-dock.js:121` call `execFile('powershell.exe', ...)`, while `reg.exe` (`:115`), `attrib.exe` (`filesystem-service.js:114-118`) and launch programs use pinned paths.
**Impact:** an unusual PATH could substitute a different executable; low likelihood on a standard Windows install.
**Next action:** use `getPinnedSystemBinary('powershell.exe')` with a System32/SysWOW64 fallback, consistent with the rest of the security module.

### Working-tree note (not a code defect)
The six modified files are an in-flight UX batch spanning three systems (shell chrome/parking, taskbar routing, Trash recycling, Win98 applets). All suites pass on this state, but there are no tests yet for the new behaviours (F6). Land them as one reviewed change with tests, or split into three reviewed changes; do not silently bundle them with a release build.

## 5. Roadmap (ordered, with acceptance criteria)

**A. Stabilise what is already in flight (next few days)**
1. Land or revert the six-file UX batch deliberately. Acceptance: `npm run verify` green; a screen recording/manual check confirms Mac OS X Discord chrome and Dock Trash work; tests added for `dtm:webapp-park`, recycle-on-drop, and real-app → shared-app taskbar routing.
2. Fix F4: re-theme/close shell windows on skin change and emit `dtm:skin-changed` after initial mount. Acceptance: test in F4 passes for all 8 skins.
3. Fix F3: source validation in all shell message listeners + http(s) allowlist in `normalizeUrl`. Acceptance: a message from a foreign source is ignored; a `file:` URL cannot reach a webview.

**B. Close the host-level security gaps (next release)**
4. Fix F1: pinned version + SHA-256/signature verification, fail-closed UX, optional bundled installer. Acceptance: tampered installer is rejected before execution; provisioning is opt-in or offline-first.
5. Fix F7: explicit media consent flow or honest "blocked" UX, matching README. Acceptance: documented behaviour matches actual callback behaviour.
6. Fix F9/F10: preload sandbox evaluation; pin PowerShell. Acceptance: full verify suite remains green.

**C. Make the architecture honest and maintainable (ongoing)**
7. Fix F2: publish one authoritative skin-trust policy; fix `LLM_SKIN_GENERATION.md`; add a review checklist for generated skins. If generated skins become a distribution feature, scope the iframe-sandbox project separately.
8. Fix F5/F8: rewrite `ARCHITECTURE.md`, retire stale phase-report claims, reconcile metadata, extract shared UI primitives one skin at a time, and make the template the canonical starting point.
9. Fix F6: CI, lint, fast unit tier, packaging/signing. Acceptance: a clean clone can run `npm ci && npm run verify` in CI and produce a signed installer.

**Non-goals for all phases:** no virtual disks, no per-skin filesystems or accounts, no storage-mode selector, no split desktop content — see §0.

## 6. Accepted/deferred risks (carried forward)

- **Host-wide filesystem access is the product model**, not a bug: a local malicious skin is trusted code (README:119, Phase 4 report:86).
- **OS-level interactions** (native tray flyouts, real screen-share picker, media permissions) cannot be fully exercised by the current test harness; policy logic is unit-tested instead.
- **Historical docs** still describe aspirational APIs; `SKIN_API_REFERENCE.md` carries a prominent status note, other docs need the same treatment (F8).
- **No packaging/signing today** — distribution is source/`npm start` only (F6).
